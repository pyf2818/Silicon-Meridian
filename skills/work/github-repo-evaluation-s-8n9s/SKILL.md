# GitHub Repository Structured Evaluation Seven-Step Method

## 适用场景
需要对一个 GitHub 开源项目做系统评估，判断其价值、质量、风险与商业前景。适用于技术选型、竞品分析、投资判断、素材沉淀等场景。

## 工作流程与步骤

### 第一步：抓取基本信息
- 从资讯流或用户输入中提取仓库全名（owner/repo）
- 抓取仓库页面（README、Stars、Forks、Commits、Issues、PRs、License、赞助商）
- 记录技术栈（从 package.json / README / 目录结构推断）
- 关键决策点：如果页面数据不完整，标记为"部分缺失"，不脑补

### 第二步：功能定位分析
- 阅读 README，提炼核心功能一句话描述
- 拆解功能模块与边界定义（哪些做、哪些不做）
- 列出技术实现细节（检测方法、算法、API 设计）
- 附加功能盘点（如知识库、工具链、CI/CD）
- 陷阱：区分"宣称的功能"与"实际实现的功能"——通过源码目录快速验证

### 第三步：代码质量评估
- 技术选型合理性（是否适合场景）
- 架构清晰度（模块化程度、目录结构、职责边界）
- TypeScript/类型系统使用完整性
- 测试覆盖（有无测试文件、CI 流水线）
- 文档完整性（README、API 文档、部署指南、i18n）
- 决策点：个人项目 vs 团队项目，质量要求不同

### 第四步：社区与生态评估
- 热度指标：Stars、Forks、趋势（是否周榜/月榜项目）
- 协作活跃度：贡献者数量、Issue 回复率、PR 合并速度
- 赞助/商业化：赞助商数量与类型、变现模式
- 更新频率：Commits 分布（集中爆发 vs 持续迭代）
- 判断标准：Stars 高但无协作 = "单兵发布"，需关注可持续性

### 第五步：竞争格局与替代方案
- 同类竞品：功能直接对标的产品
- 配套工具：互补关系（检测→解决方案链）
- 替代路径：正规替代路径（如官方 API、标准服务）
- 决策点：该工具是"独立价值"还是"生态入口"——前者强，后者弱

### 第六步：风险评估
- 技术风险：依赖逆向分析、时效性、单点故障
- 法律合规风险：灰色地带、平台政策、区域限制
- 质量风险：无测试、误报漏报、无维护承诺
- 商业风险：变现难、依赖外部生态

### 第七步：商业价值与用户价值判断
- 一句话结论模板："[仓库名] 是一个[技术定性]、[需求定性]、[热度定性]的[定位类型]开源项目，商业价值[强/中/弱/有限]"
- 对用户的具体价值：信号价值 + 技术参考价值
- 后续关注信号：增长曲线、社区转折点、外部政策变化、竞争出现

## 输出模板
评估报告使用 Markdown 表格，包含以下九大模块：
1. 一句话结论
2. 基本信息（表格）
3. 功能定位（核心功能表格 + 边界定义）
4. 代码质量（表格）
5. 社区与生态（表格）
6. 竞争格局（表格）
7. 风险与局限性（列表）
8. 商业价值判断
9. 后续关注信号（列表）

## 关键决策点
1. **区分"功能定位"与"代码质量"**：前者是做什么，后者是做得怎么样，不要混为一谈
2. **区分"社区热度"与"协作健康度"**：Stars 高不等于社区活跃，要看 Issue/PR 互动
3. **区分"商业价值"与"用户价值"**：工具对用户有用不意味着能变现
4. **证据优先原则**：所有判断必须有数据支撑，没有数据就标注"无数据"
5. **自证降档**：README 中的自我描述默认可信度降一档，优先通过源码和社区数据验证
